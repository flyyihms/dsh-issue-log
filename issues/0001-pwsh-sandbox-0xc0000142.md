# 0001 · 沙箱内 `pwsh` 一律 `0xC0000142`

| 项 | 内容 |
|---|---|
| 现象分类 | 命令执行 / Windows 沙箱 |
| 平台 | Windows 11 x64 |
| DSH | 0.2.1-rc.3（Electron 44，Node 24） |
| 严重程度 | 高：默认模式下所有 shell 命令不可用 |
| 状态 | 本地补丁已修复（一行改动），上游未跟进 |
| 关键词 | `0xC0000142`、`STATUS_DLL_INIT_FAILED`、受限令牌、默认 DACL、能力 SID |

## 症状

默认 `workspace-write` 沙箱下，**任何** `pwsh` 调用立刻退出，无任何输出：

```
命令：$PSVersionTable.PSVersion.ToString(); "sandbox-probe-ok"
结果：(no output)
退出码：3221225794 = 0xC0000142 = STATUS_DLL_INIT_FAILED
```

不是命令写错——连 `echo ok` 也一样。同一时刻在 `danger-full-access` 下完全正常。
影响面后来确认是**所有控制台子系统子进程**（`pwsh`、`cmd`），GUI 子系统进程不受影响。

## 环境

- Windows 11 x64，UAC 关闭（所有进程都是 High 完整性）
- 装有带内核驱动的国产安全软件
- PowerShell 7 曾以商店（MSIX）形式安装，后另装有独立便携版
- 复现全部在**默认沙箱**下进行；`danger-full-access` 只作为对照

## 排查思路

分四层，每层只回答一个问题：

1. **现象层**：这个退出码到底意味着什么？→ 进程在 DLL 初始化阶段就死了，脚本一行都没跑
2. **安装形态层**：是不是 PowerShell 本身的安装方式有问题？→ 换版本、换安装形态
3. **系统环境层**：是不是权限、路径、策略、杀软？→ 逐项排除
4. **实现与参数层**：沙箱到底怎么起子进程的？哪个参数决定成败？→ 复刻 + 对照实验

## 被排除的假设

| 假设 | 做法 | 结果 | 结论 |
|---|---|---|---|
| 商店版 pwsh 存根有问题 | 改装独立便携版并确认 `$PSHOME` 指向它 | 仍 `0xC0000142` | 排除 |
| PATH / 执行策略 / profile | 换工作目录、换调用方式 | 无变化 | 排除 |
| 文件 ACL | 对比两处安装目录权限 | 读写都正常 | 排除 |
| UAC 关闭导致 | 结合后续独立复刻实验 | 只是环境因素之一，非充分条件 | 排除 |
| 临时目录 / TMP 重写 | 换 temp 根、走"不管理 ACL"的旁路 | 全部一样失败 | 排除 |
| 工作区授权（ACE 写入） | 让 runner 完全不改 ACL 再跑 | 仍失败 | 排除 |
| job 对象 / 挂起创建 | 复刻 `CREATE_SUSPENDED` + kill-on-close job + resume | 正常 | 排除 |
| 宿主没有控制台 | 用 `CREATE_NEW_CONSOLE` 给宿主分配控制台再跑 | 仍失败 | 排除 |
| 安全软件用户态防护 | 退出主程序、关掉主动防御 | 仍失败 | 排除（用户态） |

到这一步可以确定：**令牌构造参数里有一个具体取值导致了失败**，而不是环境噪声。

## 转折点：三轮对照

第一轮，把沙箱执行器从宿主里拆出来单独跑，只换**模式**：

| 模式 | 子进程 | 结果 |
|---|---|---|
| `read-only` | `cmd.exe`（控制台） | 正常 |
| `workspace-write` | `cmd.exe`（控制台） | `0xC0000142` |

第二轮，固定 `workspace-write`，只换**子进程类型**：

| 子进程 | 结果 |
|---|---|
| `cmd.exe`（控制台） | `0xC0000142` |
| `wscript.exe`（GUI） | 正常，退出码 7 |

→ 沙箱本体、令牌、ACL、spawn 全都正常工作，只有控制台子进程死。问题被压到"令牌里某个只和 `workspace-write` 有关的参数"。

第三轮，用一个独立脚本直接调用同一份沙箱实现，只换**写能力 SID**：

| 写 SID（工作区 / 临时） | 结果 |
|---|---|
| 合成能力 SID / 合成能力 SID（默认） | ❌ `0xC0000142` |
| 合成能力 SID / `S-1-5-4`（交互登录组） | ✅ 正常 |
| 合成能力 SID / `S-1-1-0`（Everyone） | ✅ 正常 |
| 合成能力 SID / 用户 SID | ✅ 正常 |

规律浮出水面：**失败与否只取决于"默认 DACL 被追加的那条 ACE 指向哪个 SID"**——指向合成的 `S-1-4-…` 能力 SID 就死，指向任何可解析 SID 就正常。

再补两组反证：

| 改动 | 结果 |
|---|---|
| 跳过默认 DACL 追加 | ❌ `0xC0000142`（追加本身是必需的） |
| 追加对象改为 Everyone | ✅ 正常 |
| 追加对象改为登录 SID | ✅ 正常 |

## 根因

`workspace-write` 模式下，沙箱会在受限令牌的**默认 DACL** 上追加一条 ACE，指向它自己合成的能力 SID（`S-1-4-…`，由工作区/临时目录路径派生）。

- 这条 ACE 是必需的：子进程创建对象（含控制台相关对象）时用默认 DACL，受限令牌必须能在其中找到自己持有的 SID
- 但**合成的 `S-1-4-…` SID 在默认 DACL 里会让控制台子进程在初始化阶段失败**，返回 `STATUS_DLL_INIT_FAILED`

为什么 GUI 子进程不受影响、为什么 `read-only` 不受影响（它的默认 DACL 追加的是 Everyone），都由此解释得通。

> 推测（未验证）：`S-1-4-…` 属于"非唯一授权"，本机的安全软件内核驱动或系统组件在解析默认 DACL 时对它处理异常，导致对象创建失败。没有驱动的干净环境是否也复现，未做验证。

## 修复

一行改动，把默认 DACL 的追加对象从能力 SID 换成**登录 SID**（已在受限列表里，范围仅当前登录会话）：

```js
// 修改前
setTokenDefaultDaclGrant(api, restrictedToken, this.tempWriteSidPtr ?? this.writeSidPtr ?? worldSid);
// 修改后
setTokenDefaultDaclGrant(api, restrictedToken, logonSid);
```

- 不用 Everyone：Everyone 也能修，但把子进程创建的对象暴露给所有交互用户，范围太大
- 补丁打在打包文件里，**保持字节长度不变**（用空格补齐），避免改动包内偏移表
- 备份原包，升级后需重打

## 验证

| 检查 | 修复前 | 修复后 |
|---|---|---|
| `workspace-write` + 控制台子进程 | `0xC0000142` | ✅ 正常，退出码 7 |
| `read-only` + 控制台子进程 | 正常 | ✅ 正常 |
| 沙箱内工作区写入 | — | ✅ 成功 |
| 沙箱内工作区外写入 | — | ✅ 被拒绝（限制生效） |

最后一条很关键：修好之后**隔离仍然有效**，不是靠放宽权限换来的。

## 教训

1. `0xC0000142` 不等于"DLL 缺失或损坏"。它同样出现在受限令牌让进程初始化失败时，先看**是谁在什么权限下创建了这个进程**
2. 同一个退出码有符号/无符号两种写法（`3221225794` / `-1073741502`），日志里混用会让人以为是两回事
3. 排除法要**分层**：安装形态 → 系统环境 → 实现参数。前两层排干净，才值得去读沙箱源码
4. 能脱离宿主复现的问题，才容易做对照。把执行器单独拉出来跑，是这次的分水岭
5. 对照实验一次只动一个变量：先换模式、再换子进程类型、最后换 SID
6. "修好了"要用**隔离仍生效**来证明，否则可能只是把权限放宽了

## 复现要点（脱敏）

1. 在 `workspace-write` 模式下调用任意控制台命令，观察退出码是否为 `3221225794`
2. 用 GUI 程序（如 `wscript.exe`）做对照，确认沙箱本体正常
3. 用同一份沙箱实现，把默认 DACL 的追加对象依次换成能力 SID / Everyone / 登录 SID，观察差异
4. 修复后重复 1，并补一次工作区外写入，确认限制仍在
