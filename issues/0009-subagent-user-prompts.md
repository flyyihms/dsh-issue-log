# 0009 · 子代理会话里的 "user 消息" 是 agent 写的提示词

| 项 | 内容 |
|---|---|
| 现象分类 | 数据格式 / 会话解析 |
| 平台 | Windows 11 x64 |
| DSH | 0.2.1-rc.3 |
| 严重程度 | 中（按 0008 修完仍有"我没说过的话"） |
| 状态 | 规避方案（跳过 `delegationDepth > 0` 的会话） |
| 关键词 | subagent、delegationDepth、user/message、会话树 |

## 症状

按 0008 加了 `source.kind === "user"` 过滤后，搜索"我"仍然出现明显的机器文案：

- "你是只读探索子代理，工作目录 …"
- "仅凭你自己的通用知识回答下面的问题。不要读取任何文件，不要运行命令…"

这些**不是用户输入**，但它们的 `source.kind` 确实是 `user`。

## 环境

- DSH 0.2.1-rc.3，使用过 `subagent` / `subagent_fork`
- 会话目录下每个会话一个文件，父会话与子会话平铺存放

## 排查思路

1. 定位这些命中来自哪个会话文件。
2. 读该文件首条 `session` 事件，看会话属性（cwd、delegationDepth、isSeeded、parent）。
3. 统计全部会话里 `delegationDepth > 0` 的数量。

## 被排除的假设

| 假设 | 做法 | 结果 | 结论 |
|---|---|---|---|
| 过滤条件写错 | 复查 `kind` 判断 | 正确 | 排除 |
| 还有别的注入 kind | 全量统计 kind 取值 | 只有已知几种 | 排除 |
| 命中来自当前主会话 | 校验 session id | 来自另一个会话 | 排除 |

## 转折点

对命中的会话读首条事件：

```json
{"type":"session","id":"session-…","cwd":"<WORKSPACE>","delegationDepth":1,"isSeeded":false}
```

17 个会话里有 **3 个** `delegationDepth: 1`——正是 subagent 会话。子代理的"第一条用户消息"就是主代理写给它的任务提示词，所以 `kind` 天然是 `user`。

## 根因

**已验证**：子代理会话是一个独立会话，主代理发给它的任务描述在该会话里就是用户输入；因此"`kind: user` 即真人输入"这个假设在子会话中不成立。

**推测**：`delegationDepth` 用于表达会话树深度，0 = 用户直接发起的会话，>0 = 由代理派生。

## 修复

检索时跳过 `delegationDepth > 0` 的会话：

```js
const header = events.find((e) => e?.type === "session") ?? {};
if (Number(header.delegationDepth ?? 0) > 0) continue;
```

扫描会话数从 17 降到 14，结果只剩真人对话。

替代方案：
- 保留子会话但单独标注（"子代理"标签）：如果以后要查"我当时让子代理做了什么"会更方便，可作为开关，而不是默认。

## 验证

| 检查 | 修复前 | 修复后 |
|---|---|---|
| 搜 `agent` + 筛选"我" | 混入"你是只读探索子代理…" | 只剩真人输入 |
| 扫描会话数 | 17 | 14 |
| 明确统计 | 3 个子会话 | 3 个被跳过 |

## 教训

- "会话"不等于"和用户的对话"：代理派生出来的会话也算会话，做检索/统计时必须先按会话属性分层。
- 修完一个过滤条件后，**用"我没说过这句"再验证一次**——同一症状可能有第二层原因（0008 → 0009 就是两层）。
- 先把可能的会话属性（深度、父会话、是否种子）打印出来，比继续猜过滤规则快。

## 复现要点（脱敏）

1. 用 `subagent` 跑一个任务，产生子会话。
2. 解析子会话说日志，首条 `session` 事件含 `delegationDepth: 1`。
3. 其首条 `user/message` 的 `source.kind === "user"`，内容为主代理写的提示词。
